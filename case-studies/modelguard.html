Technical case study · Model risk and AI governance

ModelGuard

A working model risk management and AI governance platform for a fictional bank: it inventories ten financial crime models, measures them every month from the records they scored, runs independent validations and writes every change to a tamper-evident audit trail.

Who it is for

Heads of model risk management, model validators, financial crime compliance leaders and the technology teams that support them.

What I built

A FastAPI and PostgreSQL backend with role-based access, a synthetic bank scored by ten detection models, monthly monitoring with drift tests, validation and findings workflows, EU AI Act readiness assessments, LLM evaluation, committee PDFs and a hash-chained audit trail, behind a React and TypeScript front end.

Result

Every figure in a committee pack traces back to records in one database. A simulated month of severe drift shows up as graded breaches within seconds.

The problem

A bank running transaction monitoring, sanctions screening, customer risk rating and newer machine learning and LLM tools has to show its supervisors that each model is inventoried, independently validated, monitored against agreed limits and fixed when it fails. In practice that evidence lives in spreadsheets, email and slide decks, and the numbers in committee packs are typed in by hand.

The questions a Head of Model Risk Management gets asked are simple to state and hard to answer quickly: which models are breaching their limits right now, did recall fall because the model got worse or because the data broke, which findings are past target, and can we prove nobody edited the approval history?

Architecture

How data moves from source to decision.

  1. Generate a bankA deterministic generator creates 1,200 customers, 64,997 transactions, 8,139 alerts and 6,240 news articles over twelve months, with data quality defects and drift scenarios.
  2. Score with ten modelsA weighted rules engine, gradient boosting, logistic regression, TF-IDF classifiers and fuzzy name screening score every record. The two LLM systems use seeded or recorded outputs.
  3. Monitor monthlyPrecision, recall, F1, PSI, Kolmogorov-Smirnov and chi-square drift tests and data quality rates are compared with each model's limits to raise graded breaches.
  4. Validate and remediateValidations and findings move through enforced workflows with independence rules and SHA-256 hashed evidence.
  5. Govern AIAn AI system inventory, an EU AI Act readiness self-assessment, an LLM evaluation suite and outcome disparity tests.
  6. Map to regulation40 requirements and 21 controls mapped to models, with 15 automated control tests that run over live data.
  7. Report and auditAn executive dashboard, packs for three committees as PDFs and an append-only, hash-chained audit trail.

Engineering decisions

Analytics are pure functions

Metrics, PSI and drift tests have no database or framework imports, so each one is tested against values worked out by hand.

The server enforces every rule

The interface hides buttons a user cannot use, but the API checks again: a validator who owns a model cannot validate it, and a finding cannot close without remediation evidence and an independent validator.

Real detection models, not canned numbers

Monitoring reads what the models actually scored. Only the two LLM systems use seeded or recorded outputs, and the app labels them that way.

A tamper-evident audit trail

Each event stores a SHA-256 hash chained to the previous event, database triggers block updates and deletes, and a verify endpoint recomputes the whole chain.

Current guidance, no compliance claims

Controls map to the April 2026 interagency model risk guidance (SR 26-2 / OCC 2026-13), with SR 11-7 and OCC 2011-12 recorded as superseded. The EU AI Act module is an internal readiness self-assessment, not a certification.

Tests

75 pytest cases, run with one command and no network.

  • Metric, PSI and drift calculations against hand-computed values
  • Threshold breaches and severity grading
  • Validation and finding workflows, including independence rules
  • AI assessment, an LLM evaluator that catches every planted defect, and disparity testing
  • Regulatory mapping, control tests and PDF content
  • Audit chain tamper detection
  • One end-to-end workflow from drift to committee report
  • Run in CI on Python 3.9, Python 3.12 and PostgreSQL 16, plus a Docker Compose start-up check

Results

  • Gradient boosting beats the rules engine on precision by roughly three times, and both lose recall when launderers change behaviour
  • Suspicious activity model recall falls from 99.6% to 81.7% under drift, past its warning limit, with a channel input PSI of 0.156
  • 9 of 15 control tests pass; the six exceptions point at real issues such as overdue revalidations and an AI pilot running without an approved assessment
  • The LLM evaluator catches all 17 planted defects, passes all 38 clean answers and fails the production research assistant at an 11.8% hallucination rate

Limitations

  • Candela Bank and all of its data are synthetic; recall can be measured only because the generator knows the ground truth
  • The two LLM systems are simulated or replayed from recorded responses, not live model calls
  • Assessments and control tests are internal governance tools, not certifications or legal opinions
  • No hosted demo: it needs a backend and database, so it runs locally or with Docker Compose
  • Demo sign-in with synthetic users; no single sign-on

What I would build next

  • An import format so a bank can load its own scored records
  • Single sign-on and access rules per legal entity
  • A hosted read-only demo
