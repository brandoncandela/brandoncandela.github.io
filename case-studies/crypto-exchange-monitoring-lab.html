Crypto Exchange Monitoring Lab

Six SQL monitoring rules that screen a fictional exchange's deposits and withdrawals against every crypto wallet on the OFAC list and their real Tron USDT counterparties.

Who it is for

Crypto exchange compliance teams and blockchain analytics vendors deciding which transfers to stop and review.

What I built

A public-data snapshot pipeline, a seeded exchange ledger, six parameterized SQL rules, per-rule scoring and an analyst queue with an answer key.

Result

Every rule catches every customer it was built to catch; the misses on precision are realistic businesses that look risky.

The problem

An exchange has to decide, for every deposit and withdrawal, whether the counterparty is sanctioned, one step removed from a sanctioned wallet, or showing a laundering pattern such as pass-through, structuring under the Travel Rule threshold or fan-out to new wallets.

Rules that only work on clean test data are easy to write. The hard part is measuring how a rule behaves against customers whose normal business looks suspicious.

Architecture

How data moves from source to decision.

  1. Snapshot public dataOFAC SDN crypto addresses, TronGrid USDT transfers of sanctioned Tron wallets and CoinGecko prices, saved on Nov 5, 2026.
  2. Seed an exchange30 fictional customers, each doing at most one risky thing so rules can be scored.
  3. Load SQLiteCustomers, transfers, sanctioned addresses and on-chain transfers.
  4. Run six rulesOne commented SQL file per rule with a params block for windows and thresholds.
  5. Score rulesPrecision, recall and named false positives per rule.
  6. Analyst queueStatic page with evidence, next steps and an answer key.

Technologies

  • Python 3 (standard library)
  • SQLite
  • SQL: joins, CTEs, ROW_NUMBER, JSON output
  • TronGrid and CoinGecko public APIs
  • unittest
  • Vanilla JavaScript

Engineering decisions

Freeze public data in a snapshot

The lab rebuilds identically offline and in tests. Refreshing is one command, so results never drift silently.

Stop at one hop

Every alert stays explainable to an analyst. Deeper tracing is where commercial tools add value, and where false links multiply.

Design the false positives

An OTC desk, a payroll company and a busy service-like wallet are built in, because tuning judgment matters more than a perfect score.

Test at the edges

Each rule is tested exactly at its boundaries: 79% vs 80% withdrawn, 60 vs 61 minutes, $2,999.99 vs $3,000.

No keys, no server

Keyless public APIs for collection and a static page for review, so there is nothing to leak or pay for.

Tests

25 unittest cases, run with one command and no network.

  • Boundary tests for all six rules
  • Ordinary customers never alert
  • The build is identical on every run

Results

  • 26 alerts on 15 of 30 customers; 2 critical alerts for direct sanctions exposure
  • Recall is 100% on all six rules; precision is 100% for direct exposure and Travel Rule gaps and 67% for the rest
  • 10 of the 12 pass-through alerts come from one legitimate OTC desk, which a real team would tune for once

Limitations

  • Follows one hop only
  • Pulls transaction history for Tron USDT only; Ethereum addresses are screened directly
  • Does not attribute wallets to exchanges, mixers or scams
  • Uses a single price snapshot, not the price at each transfer

What I would build next

  • Customer-type tuning for OTC desks and payroll businesses
  • Ethereum history through a keyed provider behind a server-side proxy
  • Attribution labels from a vendor feed, clearly separated from raw links
