Turns 5,343 alerts from three monitoring systems into 1,240 ranked customer cases and a staffing plan that meets a regulatory deadline.

Who it is for

AML operations leaders, BSA Officers and implementation teams onboarding a bank onto new tooling.

What I built

A config-driven ingestion pipeline, a tiered entity resolver, an explainable case scorer, a capacity forecaster and a six-view operator app.

Result

Same workload, 41% fewer analyst hours, because each customer is researched once instead of once per alert.

The problem

A bank under a consent order has open alerts in three systems: an Actimize-style export, a legacy SQL rules engine and fraud team referrals. Each uses its own customer ID, date format and money format. Analysts work alert by alert, research the same customer several times, and leadership reports a raw alert count that hides where the risk is.

The real question from the BSA Officer is simple: how many analysts do we need to clear this by March 31, and which customers do we look at first?

Architecture

How data moves from source to decision.

  1. Generate exportsDeterministic generator writes three realistic, messy source files plus a hidden answer key.
  2. Onboard by configOne JSON mapping per source: columns, ID type, date and money formats, open statuses.
  3. Reconcile every rowLoaded + duplicates + closed + rejected must equal rows read, or the load fails.
  4. Resolve identitiesCrosswalk, CIF with zeros restored, account, masked account plus name, name plus DOB. Below 0.9 confidence goes to a person.
  5. Build casesOne case per customer, ranked by named point rules.
  6. Forecast capacityHandle-time assumptions and a working-day calendar give clear dates for 4 to 30 analysts.
  7. Operator appStatic app: onboarding, matching, queue, staffing slider, QA sample.

Engineering decisions

Config, not code, per source

Adding a fourth system is a new JSON file. A test onboards a semicolon-delimited source with European dates using config only.

A wrong match is worse than no match

Matches under 0.9 confidence are never auto-accepted. Two customers sharing a name stay ambiguous and go to review with both candidates listed.

Additive points instead of a model

Every case shows its score as named parts (risk rating, typology, multiple systems, volume, amount, days past SLA). Examiners can read it; a model can be benchmarked against it later.

Assumptions as named constants

Handle times and SAR rates live in one file so operations and finance can challenge them, then replace them with measured times after the pilot.

Reproducible QA sample

10% of cases drawn with a stored random seed, so an examiner can rerun the selection and get the same list.

Tests

19 unittest cases, run with one command and no network.

  • Money and date parsing across all three formats, including bad dates
  • Onboarding a brand new source with config only
  • Every resolver tier, including the ambiguous and masked-account cases that must not be guessed
  • Case grouping, score parts summing to the total, tier boundaries
  • Working-day calendar with holidays and the minimum-analyst calculation
  • Automatic match precision at least 99.5% against the answer key
  • Byte-identical output on every build

Results

  • 5,343 alerts loaded; 57 duplicates and 25 unreadable dates rejected with reasons
  • 4,923 automatic matches, all correct; 420 sent to identity review, where 25 name-only guesses would have been wrong
  • 695 customers flagged by more than one system, which no one could see before
  • Alert by alert needs 9 analysts; working by customer needs 6 and clears on March 12, 2027

Limitations

  • The bank, customers and alerts are synthetic; accuracy can be measured only because an answer key exists
  • Handle times are planning assumptions until a pilot measures them
  • Read-only: it does not write back to a case management system
  • Score weights are starting values, not calibrated to outcomes

What I would build next

  • Measured handle times from a pilot feeding the forecast
  • Write-back of case IDs to the bank's case management system
  • Reviewer roles and an audit log for identity decisions
