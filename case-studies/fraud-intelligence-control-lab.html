Fraud Intelligence & Control Lab

A fraud spike on a payments platform, turned into SQL features, a tunable control and a written decision on where to set the threshold.

Who it is for

Fraud strategy and risk operations teams deciding how to change a control without flooding the review queue.

What I built

A deterministic data generator, SQL feature engineering, an auditable point score, a threshold console tied to analyst capacity, a shared-device graph and a decision brief export.

Result

At a score of 40 the control queues 8 accounts, catches all 7 review-worthy ones and stays within 8 daily reviews.

The problem

A payments platform sees a possible fraud spike. The team has to decide which accounts enter the review queue, which signals form one incident, and how to change the control without overwhelming 8 reviews of daily capacity or treating a single shared device as proof.

Architecture

How data moves from source to decision.

  1. Generate dataDeterministic accounts, devices and transactions with seeded fraud scenarios and benign lookalikes.
  2. Model in SQLiteSchema with foreign keys and indexes.
  3. Engineer featuresSQL CTEs: shared-device peers, distinct inbound senders in 24 hours, rapid outbound amount, new foreign device amount.
  4. ScoreTransparent point score per account.
  5. ExportDashboard JSON with the threshold corridor and monitoring trend.
  6. DecideThreshold console, link graph, four-week monitoring and a downloadable brief.

Technologies

  • SQL: CTEs, time windows, aggregation

Engineering decisions

Point score over a black box

Each point maps to a signal an investigator can verify, which is what a control owner needs before a model is justified.

Capacity is a hard constraint

Every threshold shows its alert volume against the 8 daily reviews, so a better recall that the team cannot work is visible as a cost.

Labels for evaluation only

Synthetic ground truth is shown to score the control, and the page says a live team would not have it at decision time.

A shared device is a lead

The graph shows the cluster, and the brief treats it as something to check, not as proof of fraud.

Tests

7 unittest cases, run with one command and no network.

  • Foreign keys are clean and the population is as expected
  • The mule cluster is linked through its shared device
  • The account takeover feature fires, and a benign marketplace lookalike is kept
  • The threshold tradeoff is present
  • The dashboard export is valid JSON

Results

  • Score 40: 8 alerts, 87.5% precision, 100% recall, within capacity
  • Score 50: 5 alerts but recall drops to 71.4%
  • A 5-account mule cluster linked by one shared device, reconstructed as one incident

Limitations

  • All people, devices and transactions are synthetic
  • Weights are illustrative, not calibrated probabilities
  • Production would need real outcomes, ongoing monitoring and model governance

What I would build next

  • Backtesting against labeled historical outcomes
  • Champion and challenger comparison with a simple model
  • Drift alerts on feature distributions
