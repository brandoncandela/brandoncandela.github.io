Real SQLite queries running in the browser to show which monitoring threshold changes cut review work and which ones miss cases that matter.

Who it is for

Transaction monitoring and model risk teams tuning scenarios.

What I built

A deterministic fixture generator, an indexed schema, parameterized scenario queries, an in-browser SQL engine, an alert review flow and an implementation and UAT guide.

Result

Tightening thresholds visibly trades fewer alerts for missed cases, which is the failure mode tuning has to watch for.

The problem

A fintech has too many alerts. Some threshold changes reduce work; others quietly remove cases that still deserve investigation. Teams need to see both effects before they change a rule.

Architecture

How data moves from source to decision.

  1. Generate fixturesDeterministic customers, accounts and transactions with authored labels.
  2. ModelSchema with constraints and a query-driven index.
  3. QueryRapid movement, customer profile and many-to-one scenarios as parameterized SQL.
  4. Run in browserSQL.js executes the same queries as the tests.
  5. ReviewOpen an alert, see the exact SQL, write an assessment, role-play QC.
  6. ExportCase with evidence, thresholds, SQL and review history.

Technologies

Engineering decisions

The browser runs the real queries

No precomputed results, so what a reviewer sees is what the SQL returns.

Show the misses

Recall and missed cases sit next to alert volume on every change.

Index for the query, then prove it

A test checks the query plan uses the account, direction and time index.

Tests

8 unittest cases, run with one command and no network.

  • Known baseline cases and confusion counts
  • Threshold boundary inclusion
  • A repeated sender is not counted twice
  • Transactions on the wrong day are excluded
  • Duplicate IDs and orphans are rejected
  • A tighter queue can miss more, and the query uses its index

Results

  • Baseline: 18 alerts, 8 true positives, 4 review-worthy cases missed
  • Each scenario tunable live with the effect on precision and recall

Limitations

  • Small fictional test set
  • Rapid movement uses timing and similar amounts; it does not prove the same funds
  • QC is a browser role-play without real accounts or a locked audit trail

What I would build next

  • Rolling windows instead of a fixed calendar day
  • Above- and below-the-line testing samples
  • Scenario documentation in a model risk template
