AI SAR Narrative Lab

Claude drafts Suspicious Activity Report narratives where every sentence cites its evidence, plain rules check every amount, date and citation, and a person has the final say.

Who it is for

Financial crime investigators, SAR quality control teams and compliance leaders deciding how to use language models safely.

What I built

Evidence packets with citable IDs, a structured-output drafting call, a rule-based evaluator, a fault injector that tests the evaluator, and a human review log.

Result

Drafts have not been generated yet, so no pass rates are published. Every figure will come from the committed results files once they are.

The problem

Writing the narrative is the slowest part of a Suspicious Activity Report. A language model can write a first draft in seconds, but an investigator cannot file a sentence they cannot check, and a fluent draft can hide an invented amount or date.

The question is not whether a model can write, but how a bank would know which sentences to trust.

Architecture

How data moves from source to decision.

  1. Build evidence packets24 cases picked with a fixed seed from the AML Backlog Command Center. Every fact gets an ID a draft can cite.
  2. Draft with ClaudeStructured output forces five sections (who, what, when, where, why) and a citations list on every sentence.
  3. Check with rulesEvery amount, date, count, branch and account ending must appear in the records the sentence cites.
  4. Test the testerPlant one known error per copy of a draft and confirm the right rule fires.
  5. Human reviewAccept, edit or reject with a reason; edits are rescored and disagreements with the rules are logged.
  6. Static demoDrafts and scores committed as JSON; the page never calls a model.

Engineering decisions

Citations are required, not optional

The output schema makes every sentence carry its evidence IDs, so a reviewer can check any claim in one click.

Rules check the model, not another model

The evaluator is plain code, so the same draft always gets the same result and anyone can read why a sentence failed.

Test the checker with planted errors

Eight kinds of known mistakes are injected on purpose to prove each rule actually catches what it claims to.

No API key outside one machine

Only the local generator calls the API. The public demo is static, its Content Security Policy blocks outside connections, and a test scans the repo for keys.

A person signs off

The model drafts and the rules flag; the reviewer decides, and every disagreement with the rules is recorded.

Tests

49 unittest cases, run with one command and no network.

  • The packet builder rebuilds byte for byte and never exposes a full account number
  • Every evaluator rule with passing and failing sentences
  • The fault injector plants each error and the right rule catches it
  • Refusals, cut-off replies and bad JSON from the API are recorded, not hidden
  • Review validation, disagreement scoring and the secret checks

Results

  • Pending: the 24 drafts are generated offline and have not been run yet
  • Pass rates and planted-error catch rates will be published from results/evaluation.json and results/faults.json

Limitations

  • Synthetic data, and each alert carries one amount, so drafts cite alerts rather than individual transactions
  • Rules can confirm a number is in the evidence, not whether the reasoning is convincing; that is the reviewer's job
  • Amounts written in words are not checked
  • A drafting aid only: people at a bank own the filing decision

What I would build next

  • Generate the drafts and publish pass rates and catch rates
  • Transaction-level citations once alerts carry their underlying transactions
  • Agreement tracking across several reviewers
